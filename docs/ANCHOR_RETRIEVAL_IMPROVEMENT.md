# 热词检索由全量滑窗升级为 Anchor 候选检索

## 一、问题描述

原方案会对 CTC 解码得到的音素序列与全部热词逐一进行滑窗匹配和编辑距离计算。随着
热词库扩大，计算量近似线性增长。在 4,000 个热词规模下，全量检索延迟明显增加，难以
满足流式场景纯检索 P95 小于 50 ms 的要求。

## 二、根因分析

全量滑窗没有候选预筛选，每次查询都需要遍历所有热词。大量不相关热词也会进入完整
匹配、排序和临时对象分配过程，造成重复计算；Python 垃圾回收进入查询关键路径时，还会
进一步放大尾延迟。

## 三、改进建议

先使用音素 2/3/4-gram Anchor 倒排索引快速召回 Top-64 候选，再根据 Anchor 对齐位置，
只在候选附近执行原有编辑距离精排和门控。精确子串命中的热词直接并入候选，并将垃圾
回收移出连续检索关键路径。该方案保留原有评分、Top-K 和 Prompt 注入逻辑，同时将
4,000 热词规模下的纯检索 P95 稳定控制在 50 ms 以内。
