# 热词召回与端到端代码导读

本文用于代码审核和项目汇报，集中解释第一版系统中两块最核心的推理代码：

1. Temporal 2× CTC Head 如何从音频特征召回热词；
2. 召回结果如何通过 Prompt 注入 Qwen3-ASR-1.7B，并评估最终转写是否改善。

本文只解释已经实现并实际验证过的代码路径，不把尚未实现的在线服务、流式推理或生产级 Registry 描述成现状。

---

## 1. 整体链路

```text
真实音频
  ↓
Qwen3-ASR Audio Encoder
  ↓  thinker.audio_tower.ln_post，形状约为 [T, 1024]
复用的 Validation Encoder 特征缓存
  ↓
Temporal 2× CTC Head
  ↓  形状 [2T, 90] 的音素 logits
CTC posterior 解码
  ↓  去 blank、合并连续重复音素，并保留音素置信度与时间位置
逐个热词做局部音素编辑距离匹配
  ↓
热词候选分数、Ranking Top-K、Operating 触发结果
  ↓
把 Operating 候选 surface 写入葡语 Prompt
  ↓  context 参数
Qwen3-ASR-1.7B LLM Decoder
  ↓
最终文本
  ↓
严格完整词/连续词组匹配、Recall、幻觉和错误归因
```

需要首先讲清楚两个边界：

- CTC分支不是最终转写器，它只负责从当前激活的热词表中寻找可能出现的热词；
- 最终文字仍由Qwen3-ASR生成，CTC候选只是通过Prompt提供拼写参考，不能强制写入。

## 3. 热词表如何进入评分代码

入口：

```python
load_hotword_table(path, vocab=vocab, blank_id=0)
```

位置：`src/qwen_hotword/hotwords/registry.py`

每个热词在内存中表示为一个`HotwordEntry`：

```python
HotwordEntry(
    hotword_id=...,
    language=...,
    surface=...,
    normalized=...,
    words=(...),
    pronunciation=...,
    phoneme_tokens=(...),
    token_ids=(...),
    source=...,
    validation_occurrences=...,
)
```

真正参与CTC匹配的是`token_ids`，`surface`用于Prompt和最终文字匹配。

加载时会拒绝以下错误：

- 重复`hotword_id`；
- 同一语言下完全重复的音素token序列；
- token ID越界；
- 热词包含CTC blank ID 0；
- `phoneme_tokens`与`token_ids`映射出的词表内容不一致；
- 空热词表或非法JSONL记录。

这一步保证“热词表中的IPA”和“训练CTC Head时使用的90类词表”是同一个空间。

输入示意：

```json
{
  "hotword_id": "hw_001",
  "surface": "mercado financeiro",
  "language": "pt-BR",
  "phoneme_tokens": ["m", "e", "ɾ", "k", "a", "d", "u"],
  "token_ids": [27, 13, 79, 24, 2, 9, 45]
}
```

这里的示意只说明字段关系，正式文件还包含归一化文本、词列表、完整发音和来源等字段。

## 4. CTC热词召回的完整代码步骤

### 4.1 CLI解析并加载全部输入

通用入口：

```text
scripts/evaluate_hotword_scoring.py
```

它依次执行：

```python
vocab = load_phoneme_vocab(...)
hotwords = load_hotword_table(...)
cases = load_simulated_cases(...)
cache = load_disk_feature_cache(..., expected_split="validation")
report = evaluate_hotword_scoring(...)
```

主要输入：

- Validation Encoder特征缓存；
- 生成这些特征时对应的Validation Manifest；
- 90类CTC音素词表；
- Temporal 2× CTC Head checkpoint；
- 热词表；
- 每条音频对应的active hotwords和expected hotwords case文件；
- 阈值、Top-K和edit/posterior guard参数。

`load_disk_feature_cache`会确认缓存确实来自Validation，并可校验分片SHA256。训练和评分阶段不需要重新加载1.7B Encoder或重新提取特征。

### 4.2 校验并加载Temporal 2× Head

核心调用位于`evaluate_hotword_scoring`：

```python
payload = _load_checkpoint(checkpoint, vocab)
head = build_ctc_head_from_checkpoint(payload)
head.load_state_dict(payload["state_dict"], strict=True)
head.eval()
```

`_load_checkpoint`检查：

- checkpoint存在且包含`state_dict`；
- 输入维度必须为1024；
- 输出类别数必须等于当前CTC词表大小90；
- blank ID必须为0；
- checkpoint记录的完整词表顺序必须与当前词表一致。

之后还会明确拒绝非Temporal 2× Head：

```python
isinstance(head, TemporalUpsampleCtcHead)
head.time_upsampling_factor == 2
```

这样可以防止误用旧Linear Head或时间轴配置不一致的checkpoint。

### 4.3 分片读取缓存特征

代码不会一次把30GB以上的缓存全部放入内存，而是逐个读取feature shard：

```python
for descriptor in cache.shards:
    wanted = set(descriptor.sample_ids) & set(case_by_sample)
    samples = load_feature_shard(descriptor, ...)
```

只保留当前评估case所需的样本。随后按batch补零：

```python
hidden_states = pad_sequence(
    [sample.hidden_states for sample in batch],
    batch_first=True,
    padding_value=0.0,
)
input_lengths = tensor([sample.hidden_states.shape[0] ...])
```

输入形状是：

```text
hidden_states: [B, T_max, 1024]
input_lengths: [B]
```

`input_lengths`保留每条样本真实有效长度，避免把padding帧交给CTC解码。

### 4.4 Temporal 2× Head前向计算

```python
logits = head(hidden_states, input_lengths=input_lengths)
effective_lengths = head.output_lengths(input_lengths)
```

输出形状：

```text
logits: [B, 2T_max, 90]
effective_lengths: 原始有效长度 × 2
```

这里的2×时间轴是召回能力的重要基础：更长的有效时间轴给CTC更多对齐位置，尤其减少较长音素标签被删除或无法对齐的问题。

### 4.5 将CTC logits解码为音素序列

核心函数：

```python
decode_ctc_posterior(logits, input_length=..., blank_id=0)
```

位置：`src/qwen_hotword/hotwords/scoring.py`

具体步骤：

1. 只截取`logits[:input_length]`，忽略padding；
2. 对90类做`softmax`；
3. 每个时间步取概率最大的token；
4. 将连续相同token折叠为一次；
5. 删除blank token 0；
6. 为每个折叠后的音素记录：
   - `token_id`；
   - 这一连续区间的平均最大后验概率`confidence`；
   - `start_step`；
   - `end_step`。

伪代码：

```python
probabilities = softmax(logits[:input_length])
confidence, token_id = probabilities.max(-1)

for each consecutive run of the same token_id:
    if token_id != blank_id:
        decoded.append(
            DecodedPhoneme(
                token_id=token_id,
                confidence=mean(run_confidence),
                start_step=run_start,
                end_step=run_end,
            )
        )
```

得到的不是最终文字，而是类似下面的整句音素序列：

```text
[v, o, s, e, t, e, m, ...]
```

同时保留每个音素来自哪一段2×时间轴，后续可输出热词大致出现位置。

### 4.6 每个热词做局部滑窗匹配

核心函数：

```python
_score_candidate(candidate, decoded, config)
```

假设热词音素长度为`L`，代码不会拿它和整句话直接计算一次编辑距离，而是在整句解码音素中寻找最佳局部窗口。

窗口长度范围：

```python
maximum_delta = max(2, ceil(L * 0.5))
minimum_width = max(1, L - maximum_delta)
maximum_width = min(decoded_length, L + maximum_delta)
```

然后枚举所有合法`start/end`：

```python
for width in range(minimum_width, maximum_width + 1):
    for start in range(0, len(decoded) - width + 1):
        end = start + width
        distance = sequence_edit_distance(target, decoded_ids[start:end])
```

每个窗口计算：

```text
edit_ratio = 编辑距离 / max(热词音素长度, 窗口音素长度)
posterior = 窗口内所有解码音素confidence的平均值
```

最佳窗口选择顺序为：

1. edit ratio更小；
2. 原始edit distance更小；
3. posterior更高；
4. 窗口长度与目标长度更接近；
5. 如果仍相同，优先更早出现的位置。

这就是为什么热词可以出现在长句的任意位置，而不要求整句音素与热词等长。

### 4.7 最终热词分数

最佳窗口确定后：

```text
edit_similarity = 1 - edit_ratio
confidence_factor = (1 - posterior_weight) + posterior_weight × posterior
score = edit_similarity × confidence_factor
```

当前固定：

```text
posterior_weight = 0.25
```

因此可写为：

```text
score = (1 - edit_ratio) × (0.75 + 0.25 × posterior)
```

直观解释：

- 音素编辑相似度是主因素；
- CTC posterior对结果做置信度修正；
- 即使音素序列相似，如果模型本身很不确定，最终分数也会降低。

输出`HotwordMatch`包含：

- `score`；
- `edit_similarity`、`edit_distance`、`edit_ratio`；
- `posterior_confidence`；
- 匹配到的解码音素区间；
- 对应的CTC时间步范围。

### 4.8 对所有active hotwords独立评分

`score_hotwords`的主要逻辑：

```python
decoded = decode_ctc_posterior(...)
matches = [
    _score_candidate(candidate, decoded, config)
    for candidate in hotwords
    if len(candidate.token_ids) >= minimum_phonemes
]
matches.sort(...)
```

排序优先级：

1. `score`从高到低；
2. `edit_ratio`从低到高；
3. `posterior_confidence`从高到低；
4. `hotword_id`稳定排序。

一句话有多个热词时，不是先选一个标签再结束，而是100个active hotwords分别与整句音素序列匹配，最后统一排序。因此多个真实热词可以同时进入Top-5。

### 4.9 Ranking和Operating是两种不同结果

#### Ranking

```text
ranked_matches[:K]
```

只表示分数最高的前K个候选，不应用部署触发阈值。

即使音频完全不包含热词，只要active table非空，也一定能排出前K名。因此：

- Ranking Recall@K用于观察真实热词是否被排到前面；
- 负例上的Forced Top-K不能视为系统真的触发了热词；
- Ranking中的干扰词X只表示“它在所有候选中相对靠前”。

#### Operating

真正用于Prompt注入的候选必须先通过：

```python
match.score >= threshold
match.edit_ratio <= maximum_edit_ratio
match.posterior_confidence >= minimum_posterior_confidence
```

然后最多保留Top-K：

```python
selected = qualified[:top_k]
```

如果启用了`minimum_top1_margin`，前两名差距过小还可以整体抑制；当前多热词评估固定为0，因为非零margin会把两个同时真实出现且分数接近的热词一起清空。

当前v3固定Operating配置：

```text
threshold = 0.86
top_k = 5
maximum_edit_ratio = 0.35
posterior_weight = 0.25
minimum_posterior_confidence = 0.0
minimum_phonemes = 4
minimum_top1_margin = 0.0
time_axis = temporal_upsample_2x_only
```

所以干扰词X只有通过这些guard并进入最多Top-5的Operating结果，才会被当成一次实际错误候选；如果只是Forced Ranking靠前但分数不足，不会注入Qwen Prompt。

### 4.10 产生逐case评分和总体指标

通用v2代码先用一个宽松配置保存全部排序结果：

```python
score_threshold = 0.0
maximum_edit_ratio = 1.0
top_k = 全部热词
```

这样不需要每换一个阈值就重新运行Head。之后CPU侧用已有`ranked_matches`计算：

- Ranking Recall@1/3/5；
- 各音素长度分桶Recall；
- 各阈值下Precision、Recall、F1；
- 正例case hit rate；
- 负例case false-positive rate；
- 推荐Operating point。

主要输出：

```text
hotword_case_scores.jsonl
hotword_scoring_report.json
```

`hotword_case_scores.jsonl`保存每条case的全部候选评分，是后续Retrieved RAG的直接输入。`hotword_scoring_report.json`保存总体指标和配置。

## 5. v3多关键词、组合词和嵌套词评分的差异

入口：

```text
scripts/evaluate_multi_nested_hotwords.py
```

核心：

```python
score_multi_nested_cases(...)
```

它复用通用的：

- `load_hotword_table`；
- Temporal 2× Head加载；
- feature shard流式读取；
- `score_hotwords`底层局部音素匹配。

没有复制另一套热词评分算法。差异主要在Ground Truth和指标统计。

### 5.1 每条case固定100个active hotwords

每条自然Validation音频都带有：

- 真实热词；
- 对应嵌套family成员；
- 近音困难干扰词；
- 普通随机干扰词。

评分时只对该case的100个active hotwords运行匹配，而不是对全局所有热词评分。

### 5.2 同时保存两类结果

```python
ranked = all_ranked[:5]
operating = [
    match for match in all_ranked
    if score >= 0.86
    and edit_ratio <= 0.35
    and posterior_confidence >= 0.0
][:5]
```

- `ranked_matches`：Forced Top-5，仅观察排序能力；
- `operating_matches`：阈值和guard后的实际触发候选，才可进入Prompt。

### 5.3 嵌套词的两套Ground Truth

例如自然文本同时完整包含短词和长组合词：

```text
短词：São Paulo
长词：aeroporto de São Paulo
```

系统记录：

- Containment：短词和长词都属于音频中真实存在的连续词组；
- Longest-match：最终业务目标只算更长、更具体的组合词，短词属于redundant family hit。

如果音频只说了短词，没有说完整长词：

- 短词是真阳性；
- 长词若通过Operating触发，就是真正误触发。

### 5.4 多词专项指标

`evaluate_multi_nested_case_scores`计算：

- 1/2/3真实热词的Recall@1/3/5；
- Any-Hit@5和All-Hit@5；
- 三热词All-3-Hit@5；
- Mean Hits@5；
- Forced Raw Precision@5；
- Operating Precision/Recall/F1；
- 单词、非嵌套组合词、nested short、nested long分桶；
- 音素长度分桶及“形式×长度”交叉分桶；
- short-only长词误触发；
- 同一family在Top-5平均占用槽位数；
- redundant family hit数量；
- slot crowding loss和具体被挤出case。

注意：一句话有3个真实热词而Forced Ranking固定返回5个候选时，即使3个全对，Raw Precision@5也只有3/5=60%。这是指标构造的上限，不是模型准确率上限。因此汇报多热词能力时，应重点看Micro Recall@5、All-3-Hit@5和Mean Hits@5。

主要输出：

```text
hotword_case_scores_v3.jsonl
multi_nested_evaluation_report_v3.json
```

## 6. 从CTC候选到Prompt的完整代码步骤

### 6.1 端到端入口

通用v2入口：

```text
scripts/run_retrieved_rag.py
```

当前多词/嵌套v3入口：

```text
scripts/run_multi_nested_prompt_eval.py
```

两者都不再运行CTC Head，而是读取上一阶段已经生成的逐case评分：

```text
hotword_case_scores.jsonl
或
hotword_case_scores_v3.jsonl
```

因此端到端阶段可清楚拆为：

```text
离线CTC评分结果
  → Operating候选选择
  → Prompt构造
  → Qwen推理
  → 最终文本评估
```

### 6.2 加载并校验CTC逐case评分

通用函数：

```python
load_ctc_case_scores(path)
```

检查内容包括：

- 每条JSONL记录合法；
- case ID和sample ID全局唯一；
- `ranked_matches`确实按score降序；
- expected hotwords必须属于active hotwords；
- 每个ranked match也必须属于active hotwords；
- case文件、score文件、Validation Manifest中的sample和元数据一致；
- 正例热词surface必须严格存在于reference text中。

这一步防止把不同版本热词表、case和评分文件混用。

### 6.3 从Ranking中选择Operating候选

核心函数：

```python
select_ctc_matches(
    score,
    threshold=0.86,
    top_k=3或5,
    maximum_edit_ratio=0.35,
    minimum_posterior_confidence=0.0,
    minimum_top1_margin=0.0,
)
```

它重新对`ranked_matches`执行与CTC报告相同的Operating规则，然后截取Top-K。

通用v2实验固定Top-3；当前v3多词专项固定Top-5。原因是v3需要观察一句话3个真实热词及嵌套family成员同时竞争候选槽位。

这一阶段的输出是：

```python
tuple[RetrievedMatch, ...]
```

每个候选包含：

- `hotword_id`；
- `surface`；
- `score`；
- `edit_ratio`；
- `posterior_confidence`。

### 6.4 确定性选择端到端样本

通用函数：

```python
select_retrieved_rag_samples(...)
```

通用v2选择：

- 60条正例；
- 40条负例；
- 固定seed；
- 正例覆盖短、中、长热词以及单热词/多热词；
- 负例优先选择Operating已经误触发的case，再补没有触发的负例，用于压力测试Prompt污染。

因此需要注意：被选中的40条负例是故意富集困难误触发的诊断样本，不能用它们内部的误触发比例代替全Validation无偏FPR。正式CTC FPR来自完整CTC评分报告。

v3函数：

```python
select_multi_nested_prompt_samples(...)
```

固定50条audio-disjoint case：

```text
three_independent:          10
nested_family_plus_two:     10
nested_long_present:         8
two_independent:             6
nested_short_only:           3
single_hotword:              3
negative:                   10
```

同一组内优先选择Operating错误候选较多的case，再按固定seed稳定排序，便于观察多词和嵌套场景的风险。

### 6.5 模型只加载一次

核心代码：

```python
config = ModelConfig(
    path=model,
    expected_name="Qwen3-ASR-1.7B",
    dtype="bfloat16",
    device="cuda:0",
    local_files_only=True,
)
wrapper = load_asr_model(config)
```

`wrapper`在Baseline、Retrieved和Oracle三路循环之前创建一次，报告明确记录：

```text
model_load_count = 1
```

三路实验共享同一个模型实例，避免重复加载1.7B权重造成额外时间和显存抖动。

### 6.6 固定Prompt如何构造

核心函数：

```python
build_hotword_prompt(injected_surfaces, template=...)
```

固定葡语模板：

```text
As palavras a seguir podem aparecer no áudio e servem apenas como referência
de grafia. Use-as somente se forem realmente faladas; não as inclua à força
na transcrição: {hotwords}
```

语义是：

```text
以下词语可能出现在音频中，只作为拼写参考。
只有音频真正说出时才使用，不要强制加入转写。
```

构造步骤：

1. 每个surface做Unicode NFKC；
2. 去掉首尾空格；
3. 使用严格归一化结果去重；
4. 保留原surface的显示拼写和原始顺序；
5. 使用逗号拼接后填入唯一的`{hotwords}`占位符；
6. 空候选返回空Prompt。

模板必须且只能包含一个`{hotwords}`，否则直接报错。

### 6.7 Baseline路径

对全部选中音频运行：

```python
_transcribe_one(
    wrapper,
    sample,
    mode="baseline",
    injected_ids=(),
    injected_surfaces=(),
    retrieval_matches=(),
    prompt="",
)
```

Baseline没有注入任何热词，用于回答：原始Qwen3-ASR本来能写对多少热词？

每条Baseline结果缓存到：

```python
baseline_by_case[case_id]
```

供Retrieved和Oracle对照使用。

### 6.8 Retrieved Prompt路径

如果CTC Operating有候选：

```python
injected_ids = tuple(match.hotword_id for match in selected_matches)
injected_surfaces = tuple(hotword_by_id[id].surface for id in injected_ids)
prompt = build_hotword_prompt(injected_surfaces)

_transcribe_one(
    wrapper,
    sample,
    mode="retrieved_prompt",
    injected_ids=injected_ids,
    injected_surfaces=injected_surfaces,
    retrieval_matches=selected_matches,
    prompt=prompt,
)
```

如果CTC没有任何Operating候选，代码不重复调用模型：

```python
_reuse_baseline(..., mode="retrieved_prompt")
```

因为空Prompt与Baseline完全相同，直接复用既节省推理，也保证这条对照不会受随机性或重复解码影响。

### 6.9 Oracle Prompt路径

Oracle只对正例运行，直接注入Ground Truth热词：

```python
build_hotword_prompt(sample.expected_surfaces)
```

它回答的是：如果检索100%正确，Prompt/Decoder理论上是否有能力把目标热词写出来？

三路结果的意义：

| 路径 | 注入内容 | 回答的问题 |
|---|---|---|
| Baseline | 无 | 原始模型本身表现如何 |
| Retrieved | CTC Operating候选 | 当前完整系统实际能改善多少 |
| Oracle | 真实热词 | Prompt/Decoder的能力上限和剩余Decoder问题 |

### 6.10 Qwen官方Prompt接口

真正调用模型的位置是`_transcribe_one`：

```python
results = wrapper.transcribe(
    audio=sample.audio_path,
    context=prompt,
    language="Portuguese",
    return_time_stamps=False,
)
```

关键参数：

- `audio`：真实Validation音频路径；
- `context`：空字符串或热词Prompt；
- `language="Portuguese"`：固定葡语；
- `return_time_stamps=False`：本轮只关心最终文本。

代码还会确认：

- 单音频调用返回Sequence；
- 结果数量必须恰好为1；
- 第一个结果必须暴露字符串`text`字段。

项目没有修改Qwen3-ASR内部结构，也没有把热词强行写到Decoder输出中；使用的是官方wrapper已经支持的`context`参数。

### 6.11 最终文本如何判断热词是否写对

核心函数：

```python
normalize_match_words(text)
strict_phrase_match(text, phrase)
strict_matched_surfaces(text, surfaces)
```

归一化规则：

1. Unicode NFKC；
2. `casefold()`；
3. Unicode类别以`P`开头的标点替换为空格；
4. 连续空白压成一个空格；
5. 按完整单词切分。

匹配方式是连续完整word tuple相等：

```python
text_words[start:start + len(phrase_words)] == phrase_words
```

因此：

```text
coisa != coisas
relacionamento != relacionamentos
```

多词热词必须作为连续完整词组出现，不做substring匹配，不自动加入单复数、拼写alias或口语alias。

### 6.12 每条prediction记录什么

`RetrievedRagPrediction`保存：

- case/sample/audio/reference；
- Qwen最终prediction；
- 注入的hotword ID和surface；
- 对应CTC retrieval match与分数；
- 实际Prompt全文；
- Ground Truth热词；
- 最终严格匹配到的expected和injected热词；
- 简单word edit distance和reference word count；
- 本次推理耗时；
- 是否直接复用了Baseline；
- mode：baseline/retrieved_prompt/oracle_prompt。

这些字段使最终报告中的每一个数字都能追溯到具体case。

## 7. 端到端错误归因如何实现

### 7.1 Retrieval Miss

```text
真实热词不在CTC Operating候选中
```

代码：

```python
missing_retrieval = expected - selected
```

说明问题在CTC召回、热词评分、阈值或Top-K阶段，Decoder根本没有收到正确热词。

### 7.2 Decoder Miss

```text
CTC正确召回并注入，但Qwen最终文本仍没有严格写出
```

代码：

```python
retrieved_expected = expected & selected
missed_after_prompt = retrieved_expected - final_expected
```

说明检索正确，但Prompt没有成功改变最终Decoder输出。

### 7.3 Hotword Rescue

```text
Baseline没写对，Retrieved Prompt写对
```

代码：

```python
rescued = (retrieved_expected - baseline_expected) & final_expected
```

这是真正能证明端到端热词链路带来正向收益的case。

### 7.4 Wrong Candidate Injected

```python
wrong_ids = selected - expected
```

表示CTC Operating选中了音频里不该有的热词并把它注入Prompt。注意“错误候选被注入”不等于“最终发生幻觉”。

### 7.5 Wrong Candidate Written

```python
written_wrong = wrong_ids & matched_injected
```

错误候选不仅被注入，而且最终转写中严格出现了该词。

### 7.6 Newly Written Wrong Candidate

代码还会检查Baseline本来是否已经写出这个词：

```python
new_written_wrong = written_wrong - baseline_written_wrong
```

只有Baseline没有、Retrieved新增的错误热词，才更接近“Prompt引入的新幻觉”。报告计算：

```text
new_wrong_candidate_hallucination_rate
= 新增错误写入数量 / 错误注入候选数量
```

### 7.7 v3嵌套词的特殊归因

在v3中：

```python
wrong = selected - expected - redundant
```

其中：

- `expected`：Longest-match目标；
- `redundant`：同一family内自然包含、但不是最终最长目标的短词；
- `wrong`：真正无关的错误候选。

因此长组合词和其中的短词同时进入Top-5时，短词会被记录为`redundant_family_candidates_injected`，不会误算成真正幻觉。

## 12. 审核时常见问题

### 12.1 为什么不用CTC直接生成最终转写？

因为CTC Head只训练了90类音素，目标是低成本判断热词发音是否出现，不承担标点、语义、语言模型和完整文字生成。最终转写仍交给Qwen3-ASR Decoder。

### 12.2 为什么热词表可以在线更新而不用重新训练？

CTC Head输出固定的90类音素后验。新热词只要通过G2P转换成同一套音素token ID，就可以作为新的匹配序列参与评分，不需要改变Head权重。当前仓库完成的是离线表加载和评估，生产级在线reload服务仍是后续工作。

### 12.3 多个热词为什么可以同时召回？

每个active hotword都独立在整句音素序列中寻找最佳局部窗口，最后统一排序，不是整句只做一次单标签分类。因此不同位置的多个真实热词可以同时进入Top-K。

### 12.4 高排名干扰词会不会直接注入？

不一定。Forced Ranking只看相对名次；只有同时通过score threshold、maximum edit ratio、posterior guard并进入Operating Top-K的候选才会注入Prompt。

### 12.5 为什么既看Recall@5又看阈值后Recall？

Recall@5诊断排序能力：正确热词有没有在候选前列。Operating Recall诊断真实部署能力：加上误触发控制后最终还能保留多少正确热词。前者高、后者低通常说明阈值较保守；两者都低才更像是CTC或匹配本身召回不足。

### 12.6 Prompt会不会把错误词强行写进去？

模板明确要求“只有真正说出时才使用”，但仍需用负例和错误候选做实测。代码分别统计错误候选注入、错误词最终写入，以及相对Baseline新增的错误写入，最后一项最接近Prompt引入的新幻觉。

### 12.7 Oracle Prompt为什么重要？

Oracle绕开CTC检索，直接给Decoder正确热词。如果Oracle仍不改善，说明瓶颈可能在Prompt接口、样本本来已被Baseline识别，或Decoder并未采用提示；如果Oracle明显高于Retrieved，则说明主要提升空间在CTC召回和候选选择。

### 12.8 当前端到端是否等于生产系统？

不是。当前已经跑通并可审计的是Validation离线评估链路：读取预先生成的CTC score，再注入Prompt并比较三路结果。尚未包含在线音频服务、热词Registry热更新、低延迟并发、流式状态管理和生产阈值校准。

## 13. 汇报时可直接使用的总结

> 我们先复用Qwen3-ASR Audio Encoder的1024维特征，通过Temporal 2× CTC Head输出90类音素后验。代码对CTC结果做argmax、连续重复折叠和blank删除，同时保留音素置信度与时间位置。每个在线热词预先由G2P转换成同一套音素token序列，再独立地在整句解码音素中进行局部滑窗编辑距离匹配。最终分数以音素编辑相似度为主，并由CTC posterior置信度修正。Forced Ranking用于衡量候选排序能力，真正注入Qwen的Operating结果还必须通过0.86分数阈值、0.35最大编辑比例等误触发控制。通过筛选的热词surface被写入固定葡语Prompt，并通过Qwen3-ASR官方`transcribe`接口的`context`参数注入。端到端评估同时运行无Prompt Baseline、CTC Retrieved Prompt和真实热词Oracle Prompt，再使用严格完整词/连续词组匹配计算最终热词Recall，并将问题拆分为CTC漏召回、召回正确但Decoder未写出、Prompt救回以及错误候选导致的新幻觉。整个过程不修改Qwen内部结构，也不使用CTC强制最终文本。
