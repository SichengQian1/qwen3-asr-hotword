# 第一版巴葡数据与 G2P 审计说明

本文用于代码汇报，说明 Noah 500 小时巴西葡萄牙语语料从原始 TSV 审计、
唯一词表生成、MFA G2P、字典审计到逐条训练数据筛选的真实调用链。

需要先区分三个不同阶段：

```text
原始数据审计
→ 生成唯一词表并调用 MFA G2P
→ 审计 G2P 字典，再按每条音频生成 ready/review Manifest
```

## 1. 原始数据审计

### 1.1 入口脚本与核心函数

命令行入口：

```text
scripts/audit_training_tsv.py
```

核心实现：

```text
src/qwen_hotword/training/data_audit.py
audit_training_tsv()
```

入口脚本只负责解析参数、调用核心函数、打印或保存 JSON；真正的审计逻辑在
`audit_training_tsv()` 中，便于单元测试和其他代码复用。

### 1.2 输入

原始 Noah 500 小时数据：

```text
TSV:
/host_home/z00841352/27A/data/Noah_espt/tsv/pt_tsv/500小时巴西葡萄牙语口语化语音数据.tsv

Audio root:
/host_home/z00841352/27A/data/Noah_espt/noah_pt

Required TSV columns:
audio, text
```

TSV 中的 `audio` 是相对路径，实际音频路径按下面的方式解析：

```text
audio_path = audio_root / audio
```

### 1.3 调用命令

先抽查前 1,000 条：

```bash
python scripts/audit_training_tsv.py \
  --tsv "/host_home/z00841352/27A/data/Noah_espt/tsv/pt_tsv/500小时巴西葡萄牙语口语化语音数据.tsv" \
  --audio-root /host_home/z00841352/27A/data/Noah_espt/noah_pt \
  --max-records 1000 \
  --sample-count 5 \
  --output outputs/noah_pt_full_500h/audit_first_1000.json
```

确认路径和字段正确后，全量审计时将 `--max-records` 设为 0：

```bash
python scripts/audit_training_tsv.py \
  --tsv "/host_home/z00841352/27A/data/Noah_espt/tsv/pt_tsv/500小时巴西葡萄牙语口语化语音数据.tsv" \
  --audio-root /host_home/z00841352/27A/data/Noah_espt/noah_pt \
  --max-records 0 \
  --sample-count 5 \
  --output outputs/noah_pt_full_500h/audit_full.json
```

### 1.4 审计内容

程序检查：

- TSV 是否存在，音频根目录是否存在；
- 是否包含 `audio` 和 `text` 两列；
- 每行是否有音频路径和文本；
- 相对音频路径能否解析为真实文件；
- 是否意外出现绝对音频路径；
- 是否出现重复音频路径；
- 文本最小、最大和平均字符数；
- 保存少量样本用于人工核查。

`status=pass` 的条件是：TSV 非空、所有扫描行都有音频值和文本、音频文件均能
解析，并且原始 TSV 的音频值符合预期的相对路径格式。

### 1.5 输出

输出是一个 JSON 报告，例如：

```text
outputs/noah_pt_full_500h/audit_first_1000.json
outputs/noah_pt_full_500h/audit_full.json
```

关键字段包括：

```text

absolute_audio_values
duplicate_audio_values

```

这个阶段只读原始 TSV 和音频，不修改原始文件，也不生成音素标签。

## 2. 为 MFA G2P 准备唯一词表

### 2.1 入口脚本与核心函数

命令行入口：

```text
scripts/prepare_mfa_g2p.py
```

核心实现：

```text
src/qwen_hotword/training/g2p_prep.py
prepare_mfa_wordlist()
```

### 2.2 调用命令

```bash
python scripts/prepare_mfa_g2p.py \
  --tsv "/host_home/z00841352/27A/data/Noah_espt/tsv/pt_tsv/500小时巴西葡萄牙语口语化语音数据.tsv" \
  --output-dir outputs/noah_pt_mfa_g2p \
  --text-column text \
  --max-records 0 \
  --minimum-word-count 1
```

### 2.3 输入与处理

输入是原始 TSV 的 `text` 列。处理步骤为：

```text
Unicode NFC
→ casefold
→ 统一不同形式的引号和连接符
→ 规范连续空格
→ 按 Unicode Letter/Mark 提取词
→ 统计词频并生成唯一词表
```

单词内部的 `'` 和 `-` 暂时保留，数字片段单独统计。这里保留问题形式是为了后续
审计，不代表这些形式会直接进入训练。

### 2.4 输出

```text
outputs/noah_pt_mfa_g2p/words.txt
outputs/noah_pt_mfa_g2p/word_counts.tsv
outputs/noah_pt_mfa_g2p/character_counts.tsv
outputs/noah_pt_mfa_g2p/fragments_with_digits.tsv
outputs/noah_pt_mfa_g2p/summary.json
```

其中：

- `words.txt`：交给 MFA 的去重词表；
- `word_counts.tsv`：每个词在真实语料中的出现次数，用于加权覆盖率审计；
- `character_counts.tsv`：字符分布；
- `fragments_with_digits.tsv`：包含数字的原始片段；
- `summary.json`：处理记录数、总词数、唯一词数等汇总。

Noah 500 小时语料实际得到：

```text
Corpus word tokens: 5,348,219
Unique words:       76,744
```

先去重再运行 G2P，可以避免对 534 万个重复词逐个预测，同时保证相同拼写使用一致
发音，并能够明确审计哪些唯一词生成失败。

## 4. 从多语言 IPA 音素集合建立固定 90 类 CTC 词表

### 4.1 先区分“建立词表”和“使用词表”

这一步包含两个不同动作：

```text
离线词表设计：
三种语言的MFA phone inventory
→ 规范化、合并、人工检查
→ 固定的90类JSON词表

训练标签生成：
某个单词的MFA IPA发音 + 固定JSON词表
→ CTC phoneme tokens和token IDs
```

90类词表不是在处理每句话时临时统计出来的，也不是只从Noah巴葡语料中自动生成。
它是面向英语、拉美西语和巴西葡语热词任务预先建立并版本化的共享音素空间。

### 4.2 词表建立的输入

v0.2使用三套成熟MFA字典的phone inventory作为权威输入：

```text
English (US) MFA dictionary v2.0.0:                 68 phones
Spanish (Latin America) MFA dictionary v2.0.0:     33 phones
Portuguese (Brazil) MFA dictionary v2.0.0:         40 phones
```

这里使用的是各MFA字典支持的音素集合，不是把三套字典中的全部单词放进CTC词表。
CTC词表的基本单位是phone，而不是word或BPE subword。

相关设计记录：

```text
docs/PHONEME_VOCAB.md
```

固定配置：

```text
configs/phonemes/en_es_ptbr_precision_ipa_vocab.v0.2.json
```

### 4.3 核心建立原理

整体过程是：

```text
English MFA phones
Spanish Latin America MFA phones
Portuguese Brazil MFA phones
        ↓
Unicode和MFA IPA-like形式规范化
        ↓
按规范化后的精确音素符号取并集
        ↓
人工保留对热词区分有价值的音素对立
        ↓
加入CTC特殊Token并固定数组顺序
```

#### 共享全局音素空间

相同音素不添加语言前缀，而是共享一个ID：

```text
不采用：EN_a / ES_a / PT_a
采用：  a
```

语言和方言保存在Manifest及热词表的metadata中，不编码进音素名称。这样可以让跨语言
同音素共享CTC输出节点，也避免输出类别因语言数线性膨胀。

#### 精度优先，不为了缩小词表强行合并

项目目标是热词和近音词区分，因此保留可能影响热词误触发的对立，例如：

```text
i / ɪ
u / ʊ
e / ɛ
o / ɔ
r / ɾ
t / t̪
d / d̪
ʃ / ʒ
tʃ / dʒ
ɐ / ɐ̃
```

巴葡鼻化元音和鼻化滑音也单独保留：

```text
ɐ̃  ẽ  ĩ  õ  ũ  j̃  w̃
```

如果为了减少类别数把这些音素提前合并，CTC Head会失去部分近音热词区分能力。

### 4.4 为什么最终是 90 类

三套phone inventory规范化并取精确符号并集后得到88个共享音素，再加入两个特殊
Token：

```text
2 special tokens
+ 88 shared IPA-like phone tokens
= 90 CTC output classes
```

前两个ID固定为：

```text
0: <blank>
1: <unk>
```

后续ID由JSON中 `tokens` 数组的位置决定，例如：

```text
2:  a
10: dʒ
14: ẽ
41: tʃ
58: ɐ̃
79: ɾ
```

因此数组顺序属于模型接口的一部分。Manifest中的标签ID、CTC Head输出维度和已经训练
完成的checkpoint全部绑定这个顺序，不能在原版本中插入、删除或重新排序Token。

### 4.5 词表建立是否有一键生成脚本

当前仓库没有一个运行时“一键重建v0.2”的脚本。v0.2是经过来源记录、规范化策略、
精度对立检查和人工评审后固定下来的版本化配置资产，而不是每次训练前动态生成。

下面的测试负责防止词表被意外改坏：

```text
tests/test_phoneme_vocab.py
```

它检查：

- Token ID顺序稳定；
- `tokens`确实覆盖三套source inventory规范化后的并集；
- 关键近音对立没有被错误合并；
- `<blank>`和`<unk>`位置固定。

如果未来增加语言或修改音素合并策略，必须创建新的词表版本、重新生成所有Manifest
Token ID并重新训练CTC Head，不能覆盖v0.2。

### 4.6 使用固定词表将 IPA 转为 Token ID

核心代码：

```text
src/qwen_hotword/phonemes/coverage.py
load_phoneme_vocab()
tokenize_ipa_to_vocab()
```

输入：

```text
MFA输出的一个IPA-like pronunciation字符串
en_es_ptbr_precision_ipa_vocab.v0.2.json
```

处理：

```text
加载tokens数组并建立 token→ID 映射
→ 将词表phone按字符串长度从长到短排列
→ IPA与词表都转为Unicode NFD匹配形式
→ 应用少量PHONE_REPLACEMENTS
→ 删除CTC不建模的词汇重音标记
→ 从左到右做最长优先匹配
→ 记录无法匹配的oov_units
```

最长优先很重要，例如 `tʃ`、`dʒ`、`ɐ̃` 等多字符音素必须优先作为一个Token匹配，
不能先被拆成更短字符。

输出是 `TokenizationResult`：

```text
normalized_ipa
tokens
token_ids
oov_units
```

例如概念上：

```text
Input IPA:  dʒ a ɾ
Tokens:     [dʒ, a, ɾ]
Token IDs:  [10, 2, 79]
OOV units:  []
```

如果出现未知phone，当前正式Manifest不会直接用 `<unk>` 代替后继续训练，而是将该
字符记录到 `oov_units`，并把相应样本标记为 `oov_phone` 进入 `needs_review`。配置中
保留 `<unk>` 是为了定义完整接口和未来受控fallback，但第一版训练采用更严格策略。

### 4.7 这一阶段的输出和使用位置

词表设计阶段的输出：

```text
configs/phonemes/en_es_ptbr_precision_ipa_vocab.v0.2.json
```

使用词表处理某个发音后的输出保存在Manifest记录中：

```text
phonemes
phoneme_token_ids
label_length
word_pronunciations
```

字典审计还会输出实际语料中的音素统计：

```text
raw_mfa_phone_counts.tsv
normalized_vocab_phone_counts.tsv
oov_phone_counts.tsv
words_with_oov_phones.tsv
```

第一版Noah巴葡数据的MFA输出phone对v0.2词表没有phone OOV，因此实际阻塞主要来自
缺失词、连接符及CTC时间长度，而不是90类词表缺少巴葡音素。

- 按原始词频加权后的语料Token覆盖率；
- OOV音素种类、次数和按语料频率加权后的影响。

IPA到CTC Token ID的处理位于：

```text

```

它会统一Unicode组合形式、处理音素替换和重音符号，然后按最长匹配原则将IPA切分成
固定词表中的Token ID。不能匹配的字符进入 `oov_units`，不会静默忽略。

每个特征分片同时保存：


### 8.4 创建Temporal 2× Head

`train_sharded_ctc_head`通过`build_ctc_head`创建模型：

```python
head = build_ctc_head(
    head_type="temporal_upsample",
    input_dimension=1024,
    num_classes=90,
    hidden_dimension=512,
    kernel_size=5,
    dropout=0.1,
    time_upsampling_factor=2,
).to(device="cuda:0", dtype=torch.float32)
```

对应结构：

```text
Encoder ln_post特征 [B, T, 1024]
  -> LayerNorm(1024)
  -> repeat_interleave，时间轴T变为2T
  -> 1x1 Conv，1024变为512
  -> GELU + Dropout(0.1)
  -> Depthwise Conv1d，kernel=5
  -> 1x1 Context Conv，512变为512
  -> Residual + GELU + Dropout(0.1)
  -> Linear，512变为90
  -> CTC logits [B, 2T, 90]
```

Head共有`838,746`个可训练参数。

### 8.5 batch如何从磁盘组成

训练每次只读取一个特征分片。分片被还原为多条：

```text
CachedSample(
  sample_id,
  hidden_states=[T, 1024],
  token_ids=[目标音素ID序列],
)
```

`collate_cached_samples`使用`pad_sequence`将不同长度特征组成：

```text
hidden_states: [B, T_max, 1024]
input_lengths: [B]
targets:       [B, S_max]
target_lengths:[B]
```

磁盘里的Encoder特征是BF16，组成batch并送入GPU时转换成FP32。目标音素补齐位置使用
`blank_id=0`，但CTC Loss同时接收真实`target_lengths`，所以补齐部分不参与Loss。

### 8.6 Head forward如何实现2×时间轴

输入先通过LayerNorm：

```python
values = self.input_norm(hidden_states)
```

然后严格重复每个时间位置：

```python
values = torch.repeat_interleave(
    values,
    repeats=2,
    dim=1,
)
```

例如：

```text
[x1, x2, x3] -> [x1, x1, x2, x2, x3, x3]
```

因此：

```text
[B, T, 1024] -> [B, 2T, 1024]
input_lengths -> input_lengths * 2
```

代码会在上采样后、输入投影后和时序卷积后按真实`2T`长度遮蔽padding，避免补零区
以及卷积bias污染有效时间边界。

接着把1024维输入投影到512维，使用kernel size为5的Depthwise卷积学习局部时间
边界，再通过Context Conv混合通道信息，并与卷积前的512维特征做残差连接。最后
`Linear(512, 90)`输出每个时间位置的90类CTC logits。

### 8.7 CTC Loss如何计算

统一计算入口是`ctc_head.py::compute_ctc`：

```python
logits = head(hidden_states, input_lengths=input_lengths)
effective_input_lengths = head.output_lengths(input_lengths)
```

Temporal 2× Head的：

```text
effective_input_lengths = input_lengths * 2
```

随后执行：

```python
log_probs = (
    logits.float()
    .log_softmax(dim=-1)
    .transpose(0, 1)
    .contiguous()
)
```

张量形状由：

```text
[B, 2T, 90] -> [2T, B, 90]
```

再调用PyTorch CTC Loss：

```python
loss = torch.nn.functional.ctc_loss(
    log_probs,
    targets,
    effective_input_lengths,
    target_lengths,
    blank=0,
    reduction="mean",
    zero_infinity=True,
)
```

CTC不需要人工标注每个音素对应哪个音频帧。训练只提供时间序列概率、参考音素序列
以及二者真实长度，CTC会对所有能还原参考序列的合法对齐路径进行求和。

### 8.8 一个batch如何更新参数

`_train_cache_epoch`中一个batch的核心代码是：

```python
optimizer.zero_grad(set_to_none=True)
computation = compute_ctc(...)
computation.loss.backward()
torch.nn.utils.clip_grad_norm_(head.parameters(), 5.0)
optimizer.step()
```

含义依次为：

1. 清空上一batch梯度；
2. 计算Temporal Head输出和CTC Loss；
3. 反向传播；
4. 将梯度范数裁剪到最大5.0；
5. 使用AdamW更新Head参数。

Optimizer只接收`head.parameters()`。

### 8.9 为什么是分片流式训练

每个epoch先确定性打乱458个Train分片；每次只加载一个分片，再打乱分片内部样本，
按batch size 256训练。完成后释放该分片并加载下一个分片：

```text
打乱分片顺序
  -> 加载1个分片
  -> 打乱分片内样本
  -> 按256条组成batch
  -> 完成该分片训练
  -> 释放分片
  -> 加载下一个分片
```

因此不需要把全部234,181条、约30 GB Encoder特征同时载入内存。

### 8.10 Validation、学习率与checkpoint

每个epoch按以下顺序执行：

```text
完整Train一个epoch
  -> 完整评估Validation
  -> 根据Validation loss更新学习率
  -> 判断并保存best/latest checkpoint
  -> 保存optimizer/scheduler训练状态
  -> 更新metrics.jsonl
  -> 判断Early Stopping
```

Validation使用`head.eval()`和`torch.no_grad()`，不计算梯度、不更新参数。

最佳checkpoint按以下顺序选择：

```text
1. Validation PER更低
2. PER相同时Validation loss更低
```

`ctc_head_best.pt`保存最佳Head，`ctc_head_latest.pt`保存最后一个epoch的Head，
`training_state_latest.pt`同时保存Head、Optimizer、Scheduler和epoch状态，用于断点
续训。续训时会校验缓存、超参数和Head结构fingerprint，防止错误恢复到不兼容任务。

## 9. 数据与G2P阶段汇报时的简明说法

> 我们先用 `audit_training_tsv.py` 检查原始TSV字段、文本和音频路径完整性；再用
> `prepare_mfa_g2p.py` 对全量文本做Unicode规范化、词频统计和唯一词表提取。仓库
> 没有重复封装MFA，而是直接通过官方CLI调用 Brazilian Portuguese G2P模型，为
> 76,744个唯一词生成Top-1发音字典。CTC词表使用英语、拉美西语和巴葡三套MFA
> phone inventory规范化后的精确符号并集；相同IPA phone跨语言共享ID，同时保留
> 对热词区分有价值的音素对立，最终由88个phone加`<blank>/<unk>`构成固定90类。
> 生成发音后使用 `audit_mfa_dictionary.py` 检查missing word、重复发音、语料加权
> 覆盖率和CTC音素OOV。最后使用 `build_full_training_manifest.py` 生成可训练
> Manifest，再由 `build_full_training_splits.py` 按96/2/2生成Train、Validation和
> Test数据文件。



文本归一化使用Python标准库unicodedata和re实现，没有依赖第三方分词库。我们先做Unicode NFC规范化，再用casefold统一大小写，统一不同形式的单引号和连接符，最后规范空白。分词按照Unicode Letter和Mark类别逐字符处理，因此可以保留葡语重音、鼻化符号和ç。第一版没有做词干化、数字展开、单复数合并或拼写纠正，避免归一化规则擅自改变原始发音标签。


我们最终采用的是Temporal 2× CTC Head，训练入口是train_full_ctc.py，模型实现在ctc_head.py。它接收Qwen Audio Encoder的[T,1024]隐藏特征，先将时间轴严格扩展为2T，再通过512维投影、kernel size为5的Depthwise时序卷积和上下文投影，最后输出90类音素CTC logits。Head共有838,746个可训练参数。训练使用缓存的234,181条Train特征和4,835条Validation特征，采用AdamW、初始学习率3e-4和batch size 256，按分片流式训练。模型在第24个epoch提前停止，最佳Validation PER为6.76%，封存Test PER为6.78%。相较旧Linear Head的29.36% Validation PER，主要改善来自时间轴翻倍后CTC对齐空间增加，删除错误显著下降。

## 10. CTC热词召回与评分

这部分属于推理阶段。CTC Head不直接生成最终文本，而是输出音素时间序列，供热词
评分器在音素空间召回候选热词。

### 10.1 代码入口与职责

通用评分入口：

```text

```

核心实现：

```text

src/qwen_hotword/hotwords/scoring.py
  CTC贪心解码、局部窗口匹配和候选评分

src/qwen_hotword/hotwords/evaluation.py
  加载Temporal 2× Head、遍历Validation缓存并计算指标

src/qwen_hotword/hotwords/multi_nested.py
  多热词、组合词和嵌套词专项评分
```

主要调用链：

```text
evaluate_hotword_scoring.py
  -> load_hotword_table
  -> load_disk_feature_cache
  -> evaluate_hotword_scoring
  -> TemporalUpsampleCtcHead.forward
  -> score_hotwords
  -> decode_ctc_posterior
  -> _score_candidate
  -> Ranking / Operating / Precision / Recall / FPR
```

### 10.2 热词在系统中的表示

每个热词保存：

```text
hotword_id
language
surface和normalized文本
words
MFA pronunciation
phoneme_tokens
90类词表中的token_ids
```

实际CTC匹配使用`token_ids`，不是直接比较文本拼写。加载时会拒绝重复ID、同语言
重复发音、blank、越界token ID，以及`phoneme_tokens`和`token_ids`不一致的数据。

### 10.3 从CTC logits得到带置信度的音素序列

Validation缓存特征经过Temporal 2× Head后得到：

```text
[B, T, 1024] -> [B, 2T, 90]
```

`decode_ctc_posterior`对每个有效时间位置执行softmax和argmax，取得最高概率音素及其
置信度；随后合并连续重复音素并删除blank，同时保留每个音素的平均置信度和起止
时间位置。

例如：

```text
逐帧预测：blank, s, s, a, a, blank, p
CTC collapse：s, a, p
```

当前实现是轻量的`greedy argmax + CTC collapse`，不是CTC beam search、prefix
search或对全部CTC路径求关键词概率。

### 10.4 每个候选热词如何寻找匹配位置

每个active hotword独立在整句解码音素序列中滑动搜索连续局部窗口。候选窗口长度
允许在热词音素长度上下浮动：

```text
maximum_delta = max(2, ceil(热词音素数 * 0.5))
```

每个窗口与热词目标音素计算Levenshtein编辑距离，包括替换、删除和插入：

```text
edit_ratio = edit_distance / max(热词长度, 窗口长度)
edit_similarity = 1 - edit_ratio
```

窗口后验置信度是该窗口中贪心解码音素最大softmax概率的平均值。最佳窗口按以下
优先级选择：

```text
1. edit_ratio最小
2. edit_distance最小
3. posterior_confidence最高
4. 窗口长度最接近热词长度
5. 更早出现的窗口
```

### 10.5 最终评分公式

当前`posterior_weight=0.25`，最终分数为：

```text
score
=
(1 - edit_ratio)
* (0.75 + 0.25 * posterior_confidence)
```

分数主要由音素编辑相似度决定，CTC后验置信度承担25%的修正作用。每个候选同时
保存`score`、编辑距离、编辑比例、后验置信度、解码音素区间和CTC时间区间，便于
逐case审计。

### 10.6 多热词句子如何召回

一句包含多个热词时，系统不是单标签分类，也不是只保留一个热词。每个active
hotword都独立在整句音素序列中寻找自己的最佳局部窗口，之后所有候选统一排序。

例如一句自然音频包含3个真实热词，而每条case有100个active hotwords：

```text
3个真实热词分别在不同时间区域找到最佳窗口
97个干扰热词也独立评分
100个候选按score统一排序
查看3个真实热词是否进入Top-5
再应用Operating门槛
```

当前多热词专项固定参数：

```text
top_k = 5
threshold = 0.86
maximum_edit_ratio = 0.35
minimum_posterior_confidence = 0.0
minimum_phonemes = 4
minimum_top1_margin = 0.0
```

`minimum_top1_margin=0.0`表示关闭全局Top-1歧义清空，因为多热词场景下多个高分
候选可能都是真实热词。

同一个`hotword_id`即使在一句中出现多次，当前评分器也只保留得分最高的一个匹配
窗口；当前目标是判断热词是否出现，不统计出现次数。

### 10.7 Ranking与Operating必须区分

Ranking先以无阈值配置保存所有候选的完整排序，再截取Top-1/3/5：

```text
score threshold = 0
maximum edit ratio = 1
不执行歧义抑制
```

即使负例音频不包含任何热词，Ranking也会强制排出Top-5。因此Ranking只回答：

```text
真实热词在候选排序中能否进入前K名？
```

Operating结果才代表实际触发：

```python
operating = [
    match
    for match in all_ranked
    if match.score >= 0.86
    and match.edit_ratio <= 0.35
    and match.posterior_confidence >= 0.0
][:5]
```

一个候选进入Ranking Top-5但score低于0.86时，不会被触发，也不会进入后续Prompt
候选。

### 10.8 干扰词何时成为False Positive

如果干扰词只进入Ranking Top-5但未通过Operating门槛，它不是实际误触发。如果它
同时满足score、edit ratio和posterior guard，就会被错误判定为音频中出现的热词，
成为CTC False Positive。

例如：

```text
真实集合：{A, B, C}
Operating选择：{A, X, B, C}

True Positive：{A, B, C}
False Positive：{X}
Recall：3/3 = 100%
Precision：3/4 = 75%
```

这说明高Recall不能单独代表系统效果好。干扰词可能因为近音、CTC解码错误、短词
偶然匹配，或嵌套短词匹配到长组合词的一部分而获得高分。

如果完全不含热词的负例仍触发X，则该负例case记一次误触发：

```text
negative case FPR
=
至少触发一个错误热词的负例音频数
/
全部负例音频数
```

如果错误候选X之后被注入Prompt，还需继续观察Qwen是否真的把X写入最终转写。
因此要区分三个状态：

```text
进入Ranking Top-K：只是排序结果
通过Operating门槛：CTC实际召回；错误时属于CTC False Positive
出现在最终转写：端到端热词幻觉
```

### 10.9 多热词指标

```text
Micro Recall@K
= Top-K中找回的真实热词总数 / 全部真实热词总数

Any-Hit@5
= 至少找回一个真实热词的正例case数 / 正例case数

All-Hit@5
= 全部真实热词均进入Top-5的正例case数 / 正例case数

Mean Hits@5
= Top-5真实命中总数 / 正例case数

Operating Precision
= 实际触发的真实热词数 / 实际触发的全部热词数

Operating Recall
= 实际触发的真实热词数 / 全部真实热词数
```

一句只有3个真实热词而Ranking固定返回5个时，Raw Precision@5理论最高只有60%。
这不是模型准确率上限，此场景应重点看Micro Recall@5、All-3-Hit@5和Mean Hits@5。

### 10.10 嵌套词与当前限制

当热词表同时包含短词和包含它的长组合词时，例如概念上的`São Paulo`和
`aeroporto de São Paulo`，二者可以匹配同一段音频的重叠区域，并同时占用Top-5
槽位。当前专项报告分别统计Containment和Longest-match口径、family slot占用和
slot crowding，但尚未实现生产级同家族最长词抑制。

当前评分器对每条音频的每个active hotword执行局部滑窗编辑距离搜索，适合当前
每case 100个候选的可审计验证。若在线热词表扩展到数千或数万，需要增加音素Trie、
发音索引、长度预筛选或近似编辑距离索引，不能直接把当前暴力扫描当作最终大规模
生产检索器。

### 10.11 汇报时的精简说法

> CTC热词召回入口是 `evaluate_hotword_scoring.py`，核心评分实现在
> `hotwords/scoring.py`。音频特征经过Temporal 2× CTC Head得到`[2T,90]`音素
> logits，评分器对其执行softmax、贪心解码、重复音素合并和blank删除，形成带
> 置信度及时间范围的音素序列。每个active hotword以90类音素ID表示，并独立在整句
> 音素序列上滑动寻找最佳局部窗口；最终分数由音素编辑相似度和窗口平均后验置信度
> 加权得到。系统先保存无阈值候选排名用于计算Recall@1/3/5，再应用0.86 score
> threshold、0.35最大编辑比例和Top-K限制产生实际触发结果。进入Ranking不代表
> 实际触发；干扰词只有通过Operating门槛时才成为CTC False Positive，因此评估
> 必须同时查看Recall、Operating Precision和负例FPR。

## 11. CTC召回到Qwen Prompt的端到端验证

### 11.1 当前端到端范围

当前完成的是可复现的端到端评估流程：

```text
真实Validation音频
  -> Temporal 2× CTC热词评分
  -> Operating候选
  -> 热词surface文本Prompt
  -> Qwen3-ASR最终转写
  -> Baseline / Retrieved / Oracle对比
```

CTC评分和Qwen推理目前分成两个阶段，通过`hotword_case_scores*.jsonl`衔接。
Prompt评估脚本读取已固定的CTC候选，不在同一进程中重新运行CTC Head。这样能够
避免重复评分、固定召回输入，并区分召回层错误和Qwen解码层错误。

这仍是评估级端到端流程，尚未封装成共享Encoder、在线Registry和实时Prompt构造的
生产服务。

### 11.2 代码入口与调用链

通用Retrieved RAG入口：

```text
scripts/run_retrieved_rag.py
```

多热词、组合词和嵌套词50条专项入口：

```text
scripts/run_multi_nested_prompt_eval.py
```

核心实现：

```text
src/qwen_hotword/inference/retrieved_rag.py
src/qwen_hotword/inference/multi_nested_prompt.py
src/qwen_hotword/inference/hotword_prompt.py
```

通用调用链：

```text
run_retrieved_rag.py::main
  -> run_retrieved_rag
  -> load_ctc_case_scores
  -> select_ctc_matches
  -> build_hotword_prompt
  -> load_asr_model
  -> _transcribe_one
  -> Qwen3ASRModel.transcribe(context=prompt)
  -> strict_phrase_match
  -> _build_report
```

### 11.3 输入与候选选择

主要输入：

```text
Qwen3-ASR-1.7B模型
Validation Manifest
固定90类CTC词表
热词表
评估case文件
CTC case score JSONL
输出目录
```

通用Retrieved RAG smoke使用：

```text
threshold = 0.86
top_k = 3
maximum_edit_ratio = 0.35
minimum_posterior_confidence = 0.0
minimum_top1_margin = 0.0
```

最新多热词专项使用同一过滤规则，但`top_k=5`。当前Top-K属于评估配置，不应表述
为已定版的最终生产参数。

Operating候选选择：

```python
selected = [
    match
    for match in ranked_matches
    if match.score >= threshold
    and match.edit_ratio <= maximum_edit_ratio
    and match.posterior_confidence >= minimum_posterior_confidence
][:top_k]
```

只有通过Operating门槛的候选会进入Prompt；只进入Ranking Top-K但未通过阈值的
候选不会注入。

### 11.4 Prompt模板与构造

固定巴葡Prompt模板位于`inference/hotword_prompt.py`：

```text
As palavras a seguir podem aparecer no áudio e servem apenas como referência
de grafia. Use-as somente se forem realmente faladas; não as inclua à força
na transcrição: {hotwords}
```

语义是：候选词可能出现在音频中，只作为拼写参考；只有真实说出时才使用，不要
强制加入转写。

`build_hotword_prompt`会对热词surface执行NFKC规范化、去空格和去重，保持召回
顺序并用逗号连接。没有候选时返回空字符串，不生成空Prompt。

CTC侧使用IPA/token ID判断发音是否匹配；Prompt侧使用热词surface文本，为Qwen
提供最终拼写参考：

```text
IPA/token IDs -> CTC召回hotword_id -> 查询surface -> 写入Prompt
```

### 11.5 Qwen官方Prompt接口

实际推理调用：

```python
results = wrapper.transcribe(
    audio=sample.audio_path,
    context=prompt,
    language="Portuguese",
    return_time_stamps=False,
)
```

真实参数名是`context`。报告记录的接口为：

```text
method: Qwen3ASRModel.transcribe
parameter_name: context
prompt_message_role: system
audio_message_role: user
```

该路径不修改Qwen模型结构、Tokenizer或输出logits，也不强制复制热词。热词仅作为
推理时system context中的拼写参考。Qwen3-ASR-1.7B在整个实验中只加载一次，三条
评估路径复用同一模型对象。

### 11.6 Baseline、Retrieved和Oracle三条路径

Baseline：

```text
同一条音频
context=""
不注入任何热词
```

用于测量Qwen原本能正确写出多少真实热词。

Retrieved Prompt：

```text
同一条音频
注入CTC实际Operating候选
```

用于测量真实CTC召回加Prompt后的实际端到端改善。若没有候选通过Operating门槛，
代码直接复用Baseline结果，不重复执行相同的Qwen推理。

Oracle Prompt：

```text
只对正例运行
直接注入该音频真实包含的热词
```

用于估计CTC召回完全正确时，Qwen利用Prompt的能力上限。

三者关系：

```text
Baseline
  Qwen原始能力

Oracle - Baseline
  Prompt接口和Qwen可利用热词提示的潜力

Retrieved - Baseline
  当前真实CTC召回加Prompt后的实际改善

Oracle - Retrieved
  仍由CTC漏召回或错误召回造成的差距
```

### 11.7 最终文本严格匹配

Qwen输出后使用`strict_phrase_match`判断热词是否正确写入。文本执行：

```text
Unicode NFKC
casefold
标点替换为空格
空格规范化
完整连续词或词组匹配
```

不做单复数、拼写alias或词形扩展。因此`coisa`不匹配`coisas`，组合词必须在最终
文本中连续完整出现。

每条prediction保存：

```text
case/sample/audio/reference
最终prediction
mode
注入热词ID和surface
CTC retrieval match及分数
actual_prompt
真实热词
严格匹配结果
简单词错误统计
推理耗时
```

### 11.8 端到端错误归因

Retrieval Miss：

```text
真实热词未通过CTC Operating门槛
-> 未注入Prompt
```

Decoder Miss：

```text
CTC正确召回并注入
-> Qwen最终仍未写出
```

Hotword Rescue：

```text
Baseline未写出
-> CTC正确召回
-> Prompt后正确写出
```

Wrong Candidate Injection：

```text
CTC错误召回音频中不存在的热词
-> 错误候选进入Prompt
```

Wrong Candidate Written：

```text
错误候选被Qwen写入最终文本
```

Newly Written Wrong Candidate：

```text
Baseline没有该错误词
-> 错误Prompt注入后最终文本新出现该词
```

最后一种才是最明确可归因于Prompt的新热词幻觉。

### 11.10 当前限制

### 11.11 汇报时的精简说法

> 端到端推理入口是 `run_retrieved_rag.py`，最新多热词专项使用
> `run_multi_nested_prompt_eval.py`。流程读取Temporal 2× CTC产生的Operating候选，
> 将候选hotword ID映射回surface文本，再通过固定巴葡模板构造拼写参考Prompt。
> Qwen3-ASR官方接口使用`transcribe`方法的`context`参数接收该Prompt，模型只加载
> 一次，同一批样本分别运行无Prompt的Baseline、注入真实CTC召回结果的Retrieved
> Prompt和直接注入正确热词的Oracle Prompt。最终使用严格完整词/连续词组匹配
> 计算热词Recall，并将失败归因成Retrieval Miss、Decoder Miss、Hotword Rescue
> 和错误Prompt诱导的新幻觉。当前已完成可复现的Validation端到端评估，但CTC评分
> 与Qwen推理仍通过中间JSONL分阶段衔接，尚未封装成共享Encoder的在线生产服务。
